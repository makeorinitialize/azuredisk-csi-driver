# Isolated external-source hold canary

This is a **first-owner, single-allocation prototype**, not a production
multi-activation lease scheme. It protects externally owned source volumes
while allowing unrelated ordinary native traffic through durable admission.
Do **not** add the
online flag to AKS's `disk.csi.azure.com` deployment, replace its DaemonSet, reuse
its sockets, or apply this repository's static `deploy/csi-azuredisk-*.yaml`
unchanged. These are operator instructions; no cluster changes were performed
while implementing or validating this recipe.

Use the reviewed image containing this feature. The names below are examples;
all configured names must match exactly:

| Purpose | Canary value |
|---|---|
| Driver namespace | `dmstack-csi-canary` |
| Existing pinned source/application namespace | `dmstack-sources` |
| Azure CSI name (`--drivername`) | `disk.dmstack.infinitydb.io` |
| ACS CSI name (separate ACS installation) | `localdisk.dmstack.infinitydb.io` |
| Azure StorageClass | `azure-block-canary` |
| ACS StorageClass | `acs-block-canary` |
| Wire DeviceProvider ID / pool | `azure-canary-origin` / `bound-block-one` |

CSI names are **not** wire provider or pool IDs. The official addon continues
serving its existing StorageClasses and volumes under `disk.csi.azure.com`.
The separately named ACS driver additionally needs its own private VG/tag;
follow its canary instructions, not the managed ACS pool.

## 1. Establish the exclusive canary scope before traffic

Use a quiescent dedicated node/VM and an isolated disk resource group. Do not
schedule other Azure data-disk attach/detach activity on that VM during the
canary, reuse its handles through another CSI name, or permit out-of-band ARM
mutation. A distinct driver name isolates Kubernetes routing; it does not
fence another controller updating the same Azure VM's disk list.

Keep the managed addon unchanged. Restrict creation/modification of canary
StorageClasses, PVs, CompositeVolumes and external-source annotations to their trusted
controllers/operators. Pin actual namespace, node, CRD and StorageClass UIDs;
names or labels alone are insufficient.

Populate the protected JSON described in
[`pkg/devicelease/README.md`](../pkg/devicelease/README.md#active-mode-externally-owned-source-pvcs):

```json
{
  "identity": {
    "providerID": "azure-canary-origin",
    "poolID": "bound-block-one",
    "compositeCRDUID": "<actual-CRD-UID>",
    "backing": {
      "namespace": "dmstack-sources",
      "namespaceUID": "<actual-namespace-UID>",
      "nodeName": "<pinned-node-name>",
      "nodeUID": "<actual-node-UID>",
      "originDriver": "disk.dmstack.infinitydb.io",
      "cacheDriver": "localdisk.dmstack.infinitydb.io"
    }
  },
  "journalNamespace": "dmstack-sources",
  "journalName": "azure-online-domain",
  "journalUID": "<actual-ConfigMap-UID>",
  "endpoint": "0.0.0.0:37443",
  "serverCertFile": "/online/server.pem",
  "serverKeyFile": "/online/server-key.pem",
  "clientCAFile": "/online/client-ca.pem",
  "grants": [
    {"clientSHA256": "<controller-leaf-DER-SHA256-hex>", "role": "controller"},
    {"clientSHA256": "<node-leaf-DER-SHA256-hex>", "role": "node", "nodeID": "<pinned-node-name>"}
  ]
}
```

Create the domain ConfigMap **once**, offline, with the data generated by
`devicelease.InitialOnlineDomain(identity)`. Then pin its server-assigned UID
in the config. Never `apply` fresh initial data over an existing journal.
The runtime neither bootstraps missing records nor resets an uncertain one.
The facade must use the same namespace/node/driver scope and explicit wire IDs
before sealing its external source snapshot. Provider class/byte restrictions
are optional; actual values come from the exactly pinned source objects.
This bootstrap initializes only the provider hold journal, not any source PVC.
New journals use internal domain version 2 and explicit-release block policy.
Do not upgrade/reset old timed or unmarked journals in place: they are
quarantined, including old selected reservations. The facade and ACS provider
must both support `Lease.hold_policy=HOLD_POLICY_EXPLICIT_RELEASE` (field 11)
with zero deadlines. No periodic renewal component is required or supported;
native detach remains blocked until independently verified node-use release.
The current online adapter still has no installed physical open/cleanup
authority, so Validate/NODE Release remain fail-closed rather than simulated.

For an offline bootstrap manifest, save this small program as
`canary-bootstrap/main.go` in an operator checkout. It prints only the initial
journal; it makes no Kubernetes or Azure calls:

```go
package main

import (
    "encoding/json"
    "log"
    "os"

    core "k8s.io/api/core/v1"
    meta "k8s.io/apimachinery/pkg/apis/meta/v1"
    "sigs.k8s.io/azuredisk-csi-driver/pkg/devicelease"
)

func main() {
    if len(os.Args) != 2 { log.Fatal("usage: bootstrap online.json") }
    b, err := os.ReadFile(os.Args[1])
    if err != nil { log.Fatal(err) }
    var c struct {
        Identity devicelease.OnlineIdentity `json:"identity"`
        Namespace string `json:"journalNamespace"`
        Name string `json:"journalName"`
    }
    if err := json.Unmarshal(b, &c); err != nil { log.Fatal(err) }
    if c.Namespace == "" || c.Name == "" { log.Fatal("journal name/namespace required") }
    data, err := devicelease.InitialOnlineDomain(c.Identity)
    if err != nil { log.Fatal(err) }
    cm := core.ConfigMap{
        TypeMeta: meta.TypeMeta{APIVersion: "v1", Kind: "ConfigMap"},
        ObjectMeta: meta.ObjectMeta{Name: c.Name, Namespace: c.Namespace},
        Data: data,
    }
    if err := json.NewEncoder(os.Stdout).Encode(cm); err != nil { log.Fatal(err) }
}
```

```sh
go run -mod=vendor ./canary-bootstrap online.json > canary-domain.json
# Operator-only, once, after confirming the isolated scope is cold:
kubectl create -f canary-domain.json
kubectl -n dmstack-sources get configmap azure-online-domain -o jsonpath='{.metadata.uid}'
```

Copy that exact UID into `online.json` before creating the protected Secret.
An AlreadyExists result is **not** permission to overwrite/reinitialize it.

Provision an administrator-controlled `azure-online-config` Secret in the
driver namespace containing `online.json`, server keypair, client CA and
`azure.json` for an approved **canary** Azure identity. That identity needs the
normal operations on the dedicated disk group and pinned VM; do not silently
fall back to the managed addon's host credential file. The node only needs
`online.json` and `azure.json` for this enrollment slice.

After filling real pins and arranging the approved canary credentials/keypairs,
the operator can create the distinct driver namespace and Secret:

```sh
kubectl create namespace dmstack-csi-canary
kubectl -n dmstack-csi-canary create secret generic azure-online-config \
  --from-file=online.json --from-file=azure.json \
  --from-file=server.pem --from-file=server-key.pem --from-file=client-ca.pem
```

Do not replace an existing namespace/Secret owned by another installation.

## 2. Render a distinct CSI installation

Start with `charts/latest/azuredisk-csi-driver`, not an addon update. An example
`canary-values.yaml`:

```yaml
image:
  azuredisk:
    repository: <registry>/azuredisk-canary
    tag: <reviewed-immutable-tag>
driver:
  name: disk.dmstack.infinitydb.io
  featureGates:
    NodeDrivenAttachDetach: false
    KataMount: false
rbac:
  name: dmstack-azure-canary
serviceAccount:
  controller: dmstack-azure-controller
  node: dmstack-azure-node
controller:
  name: csi-dmstack-azuredisk-controller
  replicas: 1
  cloudConfigSecretName: ""
  cloudConfigSecretNamespace: dmstack-csi-canary
  metricsPort: 39604
  livenessProbe:
    healthPort: 39602
  extraArgs:
    - --online-block-domain-config=/online/online.json
    - --enable-migration-monitor=false
    - --remove-not-ready-taint=false
  extraVolumeMounts:
    - {name: online-config, mountPath: /online, readOnly: true}
  extraVolumes:
    - name: online-config
      secret: {secretName: azure-online-config, defaultMode: 0400}
node:
  cloudConfigSecretName: ""
  cloudConfigSecretNamespace: dmstack-csi-canary
  hostNetwork: true
  removeNotReadyTaint: false
  metricsPort: 39605
  livenessProbe:
    healthPort: 39603
  nodeDriverRegistrar:
    healthPort: 39607
linux:
  enabled: true
  dsName: csi-dmstack-azuredisk-node
  hostNetwork: true
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
        - matchFields:
            - {key: metadata.name, operator: In, values: ["<pinned-node-name>"]}
  extraVolumeMounts:
    - {name: online-config, mountPath: /online, readOnly: true}
  extraVolumes:
    - name: online-config
      secret:
        secretName: azure-online-config
        defaultMode: 0400
        items:
          - {key: online.json, path: online.json}
          - {key: azure.json, path: azure.json}
windows:
  enabled: false
snapshot:
  enabled: false
```

The chart's `driver.name` drives both `CSIDriver.metadata.name` and the
registrar/host socket directory:
`/var/lib/kubelet/plugins/disk.dmstack.infinitydb.io/csi.sock`.
Controller `/csi/csi.sock` is a private pod `emptyDir`. The shared kubelet
registration directory is normal; never replace the official driver's plugin
directory. Distinct host-network ports above avoid addon port collisions;
verify they are free on the chosen hosts.

Render only, without modifying a cluster:

```sh
helm template azure-online-canary ./charts/latest/azuredisk-csi-driver \
  --namespace dmstack-csi-canary --values canary-values.yaml > canary-rendered.yaml
```

The current chart has controller `extraArgs`, but **no Linux node extraArgs
setting**. Apply this explicit local Kustomize overlay; omitting the node
online flag would violate the admission domain:

```yaml
# kustomization.yaml, alongside canary-rendered.yaml
resources:
  - canary-rendered.yaml
patches:
  - target:
      kind: Deployment
      name: csi-dmstack-azuredisk-controller
    patch: |-
      apiVersion: apps/v1
      kind: Deployment
      metadata:
        name: csi-dmstack-azuredisk-controller
      spec:
        template:
          spec:
            containers:
              - name: azuredisk
                env:
                  - name: AZURE_CREDENTIAL_FILE
                    valueFrom: null
                    value: /online/azure.json
  - target:
      kind: DaemonSet
      name: csi-dmstack-azuredisk-node
    patch: |-
      apiVersion: apps/v1
      kind: DaemonSet
      metadata:
        name: csi-dmstack-azuredisk-node
      spec:
        template:
          spec:
            containers:
              - name: azuredisk
                lifecycle: null
                args:
                  - --v=3
                  - --endpoint=$(CSI_ENDPOINT)
                  - --nodeid=$(KUBE_NODE_NAME)
                  - --drivername=disk.dmstack.infinitydb.io
                  - --feature-gates=NodeDrivenAttachDetach=false,KataMount=false
                  - --cloud-config-secret-name=
                  - --allow-empty-cloud-config=false
                  - --online-block-domain-config=/online/online.json
                  - --enable-migration-monitor=false
                  - --remove-not-ready-taint=false
                  - --metrics-address=0.0.0.0:39605
                env:
                  - name: AZURE_CREDENTIAL_FILE
                    valueFrom: null
                    value: /online/azure.json
```

The canary removes the general node prestop hook; waiting for every driver's
VolumeAttachments is not a canary cleanup proof. A pod shutdown/crash retains
the durable hold instead of authorizing reclaim.

```sh
kubectl kustomize . > canary-final.yaml
```

Before any operator-approved apply, review the rendered names, namespace,
service accounts/role bindings, args, image, ports and host paths. No resource
may replace `disk.csi.azure.com` or the managed controller/DaemonSet. Add the
required domain RBAC: get/update **only** the named journal ConfigMap; direct
get on the pinned namespace/node/CRD, both StorageClasses, source PVCs/PVs and
CompositeVolumes. Preserve the normal sidecars' reviewed provisioning RBAC,
using the canary's distinct service accounts and role names.

## 3. Route only the canary class and private provider endpoint

Create a separate non-default StorageClass:

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: azure-block-canary
provisioner: disk.dmstack.infinitydb.io
parameters:
  skuName: Premium_LRS
  resourceGroup: <isolated-canary-disk-resource-group>
  attachmode: ControllerDriven
  maxShares: "1"
  cachingMode: None
reclaimPolicy: Delete
allowVolumeExpansion: false
volumeBindingMode: WaitForFirstConsumer
```

Do not override disk names to alias existing addon disks. The user/operator,
not the composite controller, supplies an existing Bound Block/RWO origin PVC
with a preformatted ext4 filesystem and an existing raw-cache PVC in the same
namespace. Use a separately installed ACS canary class
with `provisioner: localdisk.dmstack.infinitydb.io`; do not repoint an existing
official StorageClass or retag managed ACS storage.

On the actual application filesystem/RWO PVC, provide names only:

```yaml
metadata:
  name: application
  namespace: dmstack-sources
  annotations:
    dmstack.csi.infinitydb.io/origin-pvc: my-existing-origin
    dmstack.csi.infinitydb.io/cache-pvc: my-existing-cache
```

Both names refer to already Bound source claims in `dmstack-sources`, not
paths, templates or ordinal expansions. Requested application capacity equals
the actual origin size. The controller snapshots outer/source/PV/SC/node UIDs,
exact CSI drivers, handles and capacities into
`dmstack.csi.infinitydb.io/external-source-pvcs-v1`; providers independently
recheck those live pins for new admission. No source owner labels or finalizers
are required or added. Old automatic backing journals fail closed.

A private Service for the controller's authenticated endpoint can use:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: azure-online-origin
  namespace: dmstack-csi-canary
spec:
  selector:
    app: csi-dmstack-azuredisk-controller
  ports:
    - {name: provider, port: 37443, targetPort: 37443}
```

Use TLS SAN `azure-online-origin.dmstack-csi-canary.svc` (or the exact selected
private DNS name), explicit client CA and exact client-leaf grants. Point the
facade origin client at that service with wire provider ID
`azure-canary-origin`; its origin pool is `bound-block-one`. The node-side
driver does not bind this controller endpoint in the enrollment slice.

After isolated installation, verify the registered custom CSI name/socket and
its CSINode entry while the official addon remains intact. A mismatch between
`--drivername`, configured `originDriver`, SC provisioner or PV driver must
fail closed. Missing journals never fall through to ordinary admission.

Reserve returns RESERVED before native publication. Composite ControllerPublish
coordinates the exact standard origin VolumeAttachment; the normal guarded
native ControllerPublish to the pinned node must remain possible before Acquire.
Bound metadata alone is not device or stage evidence. Raw sources are never
application `volumeDevices`: the runtime owns any paired projection and the
application sees only the final filesystem.

Non-Kata assembly is on the host. For Kata, origin/cache projection is internal
to the runtime and the guest adapter assembles/mounts the final dm-cache
filesystem. A host-native cleanup receipt must not stand in for exact Kata guest
cleanup plus runtime hot-unplug.

Node-use release permits ordinary detach after verified cleanup; it is not
allocation closure. Composite PVC deletion closes only its holds/mappings and
never deletes the source PVCs/PVs/disks. If users delete sources while held,
retained provider identity still blocks unsafe native destruction; absence is
not release proof. Higher-epoch activation after a node-use release is currently
unsupported, so StatefulSet restart support is not claimed.

No automatic provisioning, fresh-format service or unconditional mkfs is active.
Old experiments are retained in the inactive archive referenced by the provider
README. Physical FD/member/cleanup authority remains independently required;
source resolution alone never advertises physical readiness.
